# 公開済みアプリのアップデート(新バージョン)

審査・安全の基準は新規と同じ(100%)。ダイスは使わない(オーナーが設計の作り直しを言った時だけ)。
(Apple / Google Play の画面や条件は変わる。要確認の項目は、現行の公式で確認する。)

## 1. 変更範囲を決める(オーナーに質問。番号で)
| 区分 | 例 | 追加で行うこと |
|---|---|---|
| 小さな修正 | 不具合、文言、軽い見た目 | `2_development.md` の該当分、回帰確認 |
| 機能の追加・変更 | 新モード、画面の追加 | 上に加え `2b_edge_cases.md`、`1b_growth.md`(差別化・薄さ)、スクリーンショットの撮り直し |
| 申告に関わる変更 | 広告・課金・SDK・権限・データ収集・年齢層・外部サービス | 下の「再申告」を全て確認。`3_submission.md` |
| 大きな刷新 | コンセプト・名前・収益化 | 新規に近い。実装前にオーナーへ確認 |

## 2. 再申告・突き合わせ(変更があるものだけ)
- プライバシー(Apple: App のプライバシー / Google: データセーフティ)と、実際の収集・送信が一致しているか。
- 年齢制限・コンテンツの申告、広告の有無、課金の内容。
- 審査メモ(新機能の再現手順、必要なアカウント・外部サービス)。
- 公開ページ(サポート・プライバシー)の内容が、新しい挙動と合っているか。

## 3. 既存ユーザー・データ
- 保存データの移行(スキーマ変更、設定の引き継ぎ)。古い版からのアップデートで壊れないか、実機で確認。
- 購入の復元、通知、権限の再要求が変わらないか。
- 最低対応 OS を上げる場合は、影響を説明してオーナーに確認。

## 4. 文面とスクリーンショット
- 「新機能(What's New)」は、実際の差分だけで書く。架空の機能・修正を足さない。
- 画面が変わった時だけ、スクリーンショットを撮り直す(変わらなければ流用できるか、現行画面で確認)。
- 申請キットは `appstore/`(差分に基づく完成原稿)。個人情報は書かない。

## 5. ビルドと提出
- バージョン番号は上げる。ビルド番号は、前回より大きくする(Google Play は `versionCode` が前回より大きい必要。公式で確認)。
- TestFlight / クローズドテストで、実機の確認をしてから提出(Apple: `workflow/testflight.md`)。
- リリース方法(手動 / 自動 / 段階的)を決める。段階的リリースは、問題があれば止められる(Apple・Google Play とも、現行の画面で確認)。
- 実装が終わるまで Archive・アップロードはしない。

## 6. 公開後
- 直後の不具合・レビューを確認する。重大なら、修正版を急ぐか、リリースの一時停止を検討(要確認)。
- 学びは、`ExperiencePoints.md` に追記候補としてオーナーに見せる。
