# randomdice: 依存度ダイス

アプリの**設計**が、このフォーマット・オーナーの指示・リサーチの、どれにどれだけ寄るかを、ダイスで決める。
毎回同じ型に収まらないようにし、アプリごとに「らしさ」と「意外性」の配分を変えるための仕組み。

## 何に効くか / 効かないか
- **効く(設計の決定のみ)**: コンセプト、機能の取捨、画面構成、体験・ルール、見た目の方向、名前案、ストアでの訴求、収益化の組み立て。
- **効かない(常に100%適用)**: 審査チェック(`review_prompts/`)、個人情報の扱い、pre-commit、申請キットの手順、
  品質・安全・法令に関わる事項、オーナーが「変更不可」と書いた点。
- つまり、ダイスで変わるのは**設計の中身**であり、**レビューや安全の基準**は変わらない。

## 振るダイス
`./scripts/roll_dice.sh` を実行する(AI が数値を自分で決めない。出た値は必ず使う)。

| ダイス | 範囲 | 意味 |
|---|---|---|
| d60 | 1〜60 (%) | **フォーマット依存度**: このフォーマット(`philosophy/`、`growth/`、標準方針)にどれだけ寄せるか |
| d40 | 1〜40 (%) | **ユーザー指示依存度**: オーナーの詳細設計書・指示(アプリの設計に関わるプロンプトのみ)にどれだけ従うか |
| 余り | 100 − d60 − d40 | **リサーチ主導の書き直し**: 新作トレンドと古い名作、競合を調べ、その結果で設計書を書き直す割合 |

- d60 と d40 の合計が100になる(60 + 40)のは、両方が最大の時だけ。それ以外は余りが出る。
- 余りが0の時、リサーチ主導の書き直しは行わない。
- ユーザー指示依存度は、アプリの設計に関するプロンプトだけが対象。進め方・禁止事項・レビューの指示は含めない。

## 余りが出た時: リサーチ主導の書き直し
次を調べたうえで、**設計書(`docs/design_brief.md`)を書き直す**。
1. **新作トレンド**: 直近で伸びている/話題の同ジャンル・隣接ジャンルのアプリ、ゲーム、機能、見せ方
2. **古い名作**: 長く愛されている作品のうち、このアプリにつながるもの(遊び方、世界観、仕組み、デザイン)。何が普遍的だったかを抽出する
3. **競合**: 同じ領域のアプリと、そのレビューの不満・欠けている点

書き直しの深さの目安(既定値。AI が根拠を添えて調整してよい):
| 余り | 書き直し |
|---|---|
| 0% | しない |
| 1〜19% | 細部の調整(文言、演出、小さな機能) |
| 20〜49% | いくつかの節を再設計(体験、画面構成、訴求) |
| 50%以上 | 設計書の大半を書き直す(ただしオーナーの「変更不可」は維持) |

- 書き直した点は `docs/deviation_log.md` に、根拠(調べた作品・競合・出典)とともに記録する。
- 調べた作品を**そのまま真似しない**。仕組みや魅力を抽出し、独自の形にする(4.3・著作権対策)。
- 大きな変更(コンセプト、ターゲット、名前、収益化、主要機能)は、実装前にオーナーへ短く確認する。

## 配分の適用方法
1. 設計の決定項目を10個以上に分解する(例: コンセプト、対象、核の1文、主要ルール、画面数、ホームの構成、色・質感、アイコン、名前、継続の仕掛け、収益化、ストア訴求)。
2. 各項目の判断の根拠を、ダイスの比率に応じて割り振る(項目数 × 比率を目安に、端数は大きい方へ)。
   - フォーマット枠: `philosophy/` と `growth/` の原則を優先して決める
   - ユーザー指示枠: 詳細設計書の記述を優先して決める
   - リサーチ枠: 調査結果(トレンド・名作・競合)を優先して決める
3. 割り振りの表を `docs/dice_log.md` か `docs/design_brief.md` に残す。
4. どの項目がどの枠で決まったかを、オーナーに表で見せる。

## 運用ルール
- ダイスを振るのは、アプリごとに**企画の最初(段階0)で1回**。やり直しは、オーナーが指示した時だけ。
- 結果は隠さず、最初にオーナーへ報告する。
- 再実装・アップデートでは振り直さず、初回の結果を引き継ぐ(オーナーが指示すれば別)。
- 「変更不可」と審査・安全の基準は、どの出目でも守る。
